# 複数 Pi 現場のトポロジ決定 — 検証用まとめ

Status: **未決（ユーザー検証待ち）**。本書は決定文書ではなく、決定のための証拠と論点の棚卸し。
日付: 2026-07-07
きっかけ: R2/R19（ネットワーク入口の認証）の設計ブレスト中に、「1サイトに複数台の Raspberry Pi が必要」という現場事実が判明し、ゲートウェイの配置モデルが未確定だと分かった。
検証方法: Claude(review-max, 最大effort) と codex(gpt-5.5, xhigh) に **同一プロンプト**で独立レビューさせ、収束/分岐を比較（同一入力なので「独立に一致＝信号」）。

---

## 0. TL;DR

- **問い**: 1サイトに rpi4b が複数台必要なとき、ゲートウェイをどう置くか。
  - **Model A**: 1台を中央ゲートウェイ（コレクタ+SQLite+出口）、他は「衛星」がネットワーク越しに送る。← **現行コーパス D2 §4 が傾いている案**
  - **Model B**: 各 Pi が完全ゲートウェイ（各自コレクタ+SQLite+出口）。
  - **Model C**: B のデータ面 + 任意の「非権威な集約読み取り層」（ただの R10 消費者）。
- **両レビューの独立した結論**: **A は不採用。B を基盤に据えるべき**（集約が要る現場だけ C の集約器を足す）。data-integrity 採点は両者とも A=2/5, B=5/5, C=5/5。
- **理由の核**: 耐久点（＝データの正本が生まれる ack の瞬間）を、センサーを UART で受けている各 Pi に置くべきで、ネットワークの先に置くべきでない。
- **重要な副次発見**: この論点は**一度も裁定されていなかった**（レガシー要件 `BQ-4` が Open のまま）。しかもコーパス内に**矛盾する2つのモデルが未突合で共存**（D2 §4=A寄り と D5=B を既に許容）。
- **帰結**: 認証設計の主戦場が **R2（入口）ではなく R10（出口）** に移る。

## 1. 確定した現場の事実（実コード/ユーザー確認済み）

| 事実 | 証拠 |
|---|---|
| デバイス→ゲートウェイの経路は各 Pi 内でローカル: sensor→BravePI transmitter→**BLE5(LongRange)**→BravePI mainboard→**UART**→Pi | `iotkit-reverse-extracted/analysis/bravepi-protocol-analysis.md:72`、`iot3_node-red/flows.json`（serial `/dev/ttyAMA0` 38400） |
| BravePI mainboard は**最大16トランスミッタ**（実用上限）。足りなければ Pi を増やす → **複数 rpi4b/サイト**。衛星も rpi4b 級 | ユーザー明言。仕様上限20/実用16: `iotkit-reverse-extracted/docs/non-functional-requirements.md:170` |
| 消費者 **YokaKit は別マシン**で **MQTT 購読者**。identity 解決に **`raspberry_pi_id`（Pi 単位）** を使う | `yokakit-next/internal/mqtt/resolver.go:128`、`internal/database/migrations/001_master_data.up.sql:26,94,112` |
| レガシー実態は構造的に「各 Pi が独立発行、集約ハブなし」（＝ Model B 相当） | `iot3_node-red/flows.json`（各 Pi の Node-RED が UART 受信→MQTT 発行）、YokaKit が `ipAddress→raspberry_pi_id` でフラットに受ける |
| MQTT が実際に流れるのは「ゲートウェイ→消費者（YokaKit）」の**出口側**。センサー入口は UART（MQTT ではない） | サブエージェント実コード確認（mqtt-in ノードは無効・debug のみ） |

## 2. 3案の定義

### Model A — 中央ゲートウェイ + 衛星（コーパス D2 §4 の想定）
- 1台 = コレクタ+SQLite+出口+retention。正本（ack 耐久点）はここ1箇所。
- 他 = 衛星（アダプタランタイムのみ）。自分の BravePI を UART で読み、**ネットワーク越しの ingest 契約（既定 HTTP）**で中央へ送る。
- 認証の主戦場 = **R2（衛星→中央の入口面）**。

### Model B — 各 Pi が完全ゲートウェイ
- 各 Pi = コレクタ+SQLite+出口+retention。耐久点は各 Pi（センサー最近傍）。
- 各 Pi が独立に消費者へ**出口契約（R10）**で送る。出口が N 本。
- 認証の主戦場 = **R10（各 Pi→消費者の出口面）**。

### Model C — B + 非権威の集約層（両レビューの推奨形）
- データ面は B と同一（各 Pi にローカル耐久点）。
- サイト俯瞰が要るとき、集約器を **「ただの R10 消費者」** として足す。**新しい正本でも権威でもない**。集約器が死んでも各 Pi の収集・custody は無傷。
- 小規模サイトは集約器なしの素の B でよい。

## 3. レビュー結果（同一プロンプト・独立）

### 採点（両者ほぼ一致）

| レンズ | A | B | C |
|---|--:|--:|--:|
| **data-integrity / custody（最重要）** | 2 | 5 | 5 |
| 故障ドメイン | 2 | 5 | 4〜4.5 |
| 現場運用性 | 3〜4 | 3 | 4 |
| コスト / SD摩耗 | 2〜3 | 3.5〜4 | 2.5〜4 |
| セキュリティ | 2.5〜3 | 4 | 3.5〜4 |
| **総合** | 負け | **勝ち** | **勝ち** |

- codex: 推奨 **B**（C は将来の集約層）。総合 B 20.5 / C 19 / A 14。
- Claude: 推奨 **C**（= B + 非権威集約器）。データ面は B。
- → **実質同一の結論**。データ面は「各 Pi 完全ゲートウェイ・耐久点ローカル」。集約器は要件次第で足す任意物。

### 独立に一致した決定的論拠

1. **耐久点は UART を受けている各 Pi に置くべき。** ack の定義は「コレクタが SQLite に commit 完了」（`D1-ingest-model.md:18-20`）。A ではこの ack がネットワーク往復の先にしか存在しない。

2. **A は「安全にした瞬間に自壊する」。** A の衛星 spool は契約上 SHOULD（MUST でない）で、しかもこの免除は ESP32 の flash 摩耗死のために書かれたもの（`D1:25-26`）——rpi4b には当てはまらない。A を data-safe にするには衛星に耐久 spool を入れる必要があり、その瞬間：
   - 同一レコードに**2回の耐久書き込み**（衛星+中央）＝ B の2倍の SD 摩耗。
   - それでも衛星 spool は**正本（ack）ではない**。
   - → 「衛星に永続 spool を積めばいい」という A 擁護の最良の反論が、そのまま A の経済的優位を消す。

3. **コーパス D2 の A 傾斜は「未検討の前提」。** 動かぬ証拠：
   - **`BQ-4`「マルチゲートウェイ展開計画」＝ Open/未定義**（`iotkit-reverse-extracted/docs/business-requirements.md:352`）。裁定された形跡がない。
   - **矛盾する2モデルが未突合で共存**：
     - D2 §4（`D2-data-authority-topology-operations.md:104-111`）＝中央+衛星（A）。ただし明示的に「**センサーが遠い場合の RPi Zero**」用に書かれている。
     - D5（`D5-series-identity.md:45-46`）＝「series 同一性はゲートウェイ局所、大域同一性=(gateway_identity, system_id)、**名寄せは上流の責務**」＝**既に Model B を正しい形として認めている**。
   - 今回の駆動要因は「16トランスミッタ上限で **rpi4b 級**が複数」＝**容量問題**であって、D2 §4 の想定した**距離問題（非力な衛星）**ではない。同じ「衛星」という語が2つの別ハード前提にまたがって使い回され、後者に「薄くて当然」を持ち込んでいる。
   - **レガシー実態も A の前例ゼロ**（各 Pi 独立発行＝B）。実装コードも "衛星" 該当0件＝**今訂正しても実装コスト0**。

4. **「箱は少ないほど良い」（D2:108）は正しい運用嗜好だが、data-integrity-first の第一原則を上書きする根拠ではない**（両者）。しかも衛星も rpi4b なら OS/更新/監督/証明書など「箱の面倒」の大半は既に負っており、軽くなるのは設定面だけ。

## 4. 帰結：認証設計の主戦場が R2 → R10 に移る

- **A を選ぶ**と、本来「信頼度の低い第三者デバイス」向けの **R2**（`responsibility-ledger.md:15`）に、「同一運用者・大きな subject 集合を背負う一等市民（衛星）」を同一経路で通すことになり、**R2 に新しい信頼段階の設計問題**を追加で負わせる。1点の誤設定＝サイト全データ流出（`D7:152-153`）。
- **B/C を選ぶ**と、主戦場は **R10/D7**＝コーパスで**最も成熟した契約面**（複数レビュー済み）。新規作業は「target 登録が N 倍」という**カーディナリティの変化のみ**。漏洩・誤設定の被害半径も Pi 単位に自然分割。
- → 当初立てた「R2 入口認証」スペックは**主戦場を取り違えていた**可能性が高い。正しくは **Model B 前提の R10 マルチゲートウェイ出口 + R19 認証**。

## 5. 付随して出た、埋めるべき穴

| 重大度 | 穴 | 出所 |
|---|---|---|
| 要再監査 | `WAL + synchronous=NORMAL` は電源断でトランザクション rollback しうる（SQLite 公式 https://sqlite.org/wal.html）。ack=耐久点の土台条件 | codex |
| Important | D7 の `(epoch, seq)` は**ゲートウェイ局所採番**。N ゲートウェイ→1消費者だと `(epoch=1,seq=1)` が Pi 間衝突しうる → 消費者は **gateway_identity 込みでカーソル/dedup をスコープ**する必要。D5:45 の gateway_identity が D7 カーソル文脈に持ち込まれていない | Claude |
| Critical | D2 の復旧表（`D2:57-64`）に**衛星/ゲートウェイ故障の行がない**。N 台常時稼働なら通常運用で想定すべき故障モード | Claude |
| Minor | `terminology.md:16` が「**the** Raspberry Pi」と単数で書き、語彙レベルで「1サイト1Pi」を暗黙化 | Claude |

## 6. 逆に A（または中央集約）が勝つ条件（バランスのため明記）

両レビューが認めた「これが真なら結論が変わる」条件：

1. **衛星が本当に非力（RPi Zero/ESP32 級）**なら、D2 §4 の元の正当化が復活し A が既定に戻る。→ 今回は「衛星も rpi4b」で**不成立**。
2. **工場 LAN が信頼できない**（Wi-Fi 中心・頻繁な瞬断）→ 注意：これは **A を助けない**。むしろ A のネットワーク依存が露呈し B/C を強める。
3. **サイト単位の単一問い合わせ面が MUST**、かつ集約器を置く上位階層が将来も一切存在しない極端な現場 → この時だけ A の単一集約に相対優位。
4. **N 台分の R22 復旧訓練を回す体制がない** → 1台だけ復旧規律を持てばよい A の運用優位が効く（**A 側の正当な利点として認める**）。
5. **複数 Pi にまたがるセンサー相関ルール（R9）を1箱で評価する要件が実在** → 中央 SQLite だけが無償で実現。ただし D7 決定1「コアは派生イベントを作らない」・「フル CEP 却下」（`responsibility-ledger.md:70`）が、この種の相関をそもそもコアの仕事として拒否済みなので、効く可能性は低い。

## 7. あなたに検証してほしい点

1. **駆動要因の切り分け**: 「複数 Pi」の理由は本当に「16台という頭数上限（容量問題）」か、それとも「BLE 到達距離でメインボードを物理分散せざるを得ない（距離問題）」か。後者なら D2 §4 の元シナリオに近づく。ただし「衛星も rpi4b」という事実は容量問題を示唆。
2. **典型 Pi 台数**: 1サイトあたり何台を想定するか（小〜中規模なら素の B、5〜10台以上なら C の集約器が効く）。
3. **運用体制**: N 台分の更新・監視・R22 復旧訓練を回せるか（回せないなら A の運用優位が上記条件4で効く）。
4. **消費者側**: YokaKit 以外の将来消費者が `raspberry_pi_id` 前提を持たず「単一の一枚岩ストリーム」を要求する可能性はあるか（現 YokaKit は Pi 単位識別前提）。

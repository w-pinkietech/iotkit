AIオペレーターはどうやってゲートウェイに触るのか

3つの接続パターン。共通原則は「ゲートウェイはインターネットからの着信(inbound)を一切受けない」こと。

まず前提: 「AIオペレーター」は2つの部品でできている
① ハーネス = エージェントの実行環境(runbook、ゲートウェイAPIを叩くツール群、認証情報、エージェントループ)。キットの一部として提供する。
② LLM = ハーネスの後ろにいる頭脳。差し替え可能(ローカルモデルでもクラウドAPIでも)。
ゲートウェイから見えるのは常に「①ハーネスからの認証済みHTTP呼び出し」だけ。LLMがどこにいるかをゲートウェイは知らないし、知る必要がない。
パターンA: 完全オフライン工場 — Wave 1(AIハーネス開発時に実証)
┌─ 工場の中 ────────────────┐
│ [3] 工場サーバー           │
│  ┌─────────┐ ┌─────────┐ │
│  │ ハーネス │→│ローカルLLM││
│  └────┬────┘ └─────────┘ │
│       │ LAN内HTTPS         │
│       │ (自己署名+ピン留め)│
│       ▼ +operatorトークン  │
│ [2] ゲートウェイ           │
│  制御プレーン(LAN待受)     │
└───────── 外に出る線なし ──┘

インターネット接続ゼロで成立。データも診断内容も工場から出ない。LLMの品質は積むモデル次第。

パターンB1: ハーネスは工場、頭脳はクラウド — Wave 1(AIハーネス開発時に実証)・推奨構成
┌─ 工場の中 ────────────────┐
│ [3] 工場サーバー           │
│  ┌─────────┐              │
│  │ ハーネス │──────────────┼──→ [4] LLM API
│  └────┬────┘  APIキーで   │    (Claude等)
│       │       outboundのみ │
│       │ LAN内HTTPS         │
│       │ (自己署名+ピン留め)│
│       ▼ +operatorトークン  │
│ [2] ゲートウェイ           │
│  制御プレーン(LAN待受)     │
└─── inboundは開けない ─────┘

外に出る線は「ハーネス→LLM API」の一本だけ(発信のみ)。ゲートウェイの姿はパターンAと完全に同一。LLMに送る情報(インシデントバンドル等)はハーネスが統制=データガバナンスの制御点が工場側にある。

パターンB2: 完全リモート運用 — Wave 2
[4] クラウド/支援者側
 ┌─────────┐ ┌─────┐
 │ ハーネス │→│ LLM │
 └────▲────┘ └─────┘
      │ 中継サーバー(relay)
      ▲
      │ ゲートウェイが自分から
      │ outboundで張る常時接続
┌─────┴─ 工場の中 ──────────┐
│ [2] ゲートウェイ           │
└───────────────────────────┘

支援機関やSIerが30現場を一元運用する形。この場合も工場側にポートは開けない——ゲートウェイが自分から外の中継点に発信して接続を維持し、その中を制御が通る(AWS IoTのsecure tunnelingと同じ発想)。工場サーバー[3]すら不要になるが、中継インフラが要るのでWave 2。なお全パターン共通で、AIのoperatorトークンは物理アクション権限に昇格不可(プロンプトインジェクション対策)。

※Wave表記はD3のWave 0/1/2体系に従う。Wave 0にAIハーネスは含まれない——柱3の価値検証は、Wave 1でAIハーネスを開発する際にWave 0稼働中の自社現場ゲートウェイに対して行う(D3決定4)。

全パターン共通の安全装置(ゲートウェイ側 R14/R19)

操作主体の識別
ハーネスは「ai-operator@現場名」という運用者アイデンティティを持つ。全操作が監査ログに残る(操作者がLLMだからこそ、人間運用より厳格に)
権限の段階
①読取診断=常時可 ②可逆操作(再起動・再接続)=AI自律可 ③不可逆操作(設定変更・更新)=dry-run必須+人間承認(スマホで「はい」)
AIが暴れても壊れない
操作カタログ外のことはそもそもできない(シェルは存在しない)。レート制限。悪い設定はR15が検証で弾き、通っても自動ロールバック
AIに届かない障害への備え
ネットワーク自体が死んだらAIは無力 → だからルールベース自己修復(R20)とローカル表示(R23)と「現場の人に電源再投入を頼む」導線が下の層にある
「SSHなしで直せる」の正確な意味: これは直し方の話(型付きAPI vs 生シェル)であって、届くかどうかの話ではありません。AIが直せるのは制御プレーンに到達できる障害まで。到達できない障害(ネットワーク全断、電源、物理)は、①ゲートウェイ自身の決定的自己修復、②現場の人への平易な指示(「白い箱のコンセントを抜き挿ししてください」)、の2層が受け持ちます。この3層(AI遠隔修復/自己修復/現場の人)の役割分担こそが運用設計の本体です。

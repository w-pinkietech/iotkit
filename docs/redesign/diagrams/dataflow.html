⤵ 合流 ⤹ — ここから先、公式か自作かの区別は存在しない(柱2)
④ コレクタ = 受理の権威+耐久点 R8 R6 R16 R17

台帳解決チェーンをコミット前に実行(D5): 送信者+subject_hint → 台帳(R7) → system_id → series_id。デバイスはseriesを知らない——解決はコレクタの仕事であり、台帳の変異(replace-hardware等)も必ずコレクタ経由。続いて契約検証で3分岐(黙って捨てない): スキーマ不一致=rejected(理由コード+近い候補を提示)/ 未知measurement_key=検疫seriesを自動実体化して受理(UIで後付けマッピング)/ 値域外=検疫フラグ付き保存(下流に流さない)

→ dedup(dedupキー=(認証済み送信者, envelope_id)。再送時にIDは不変 → 再送しても二重登録されない)→ received_atを必ず付与(時刻は二本立て: デバイス申告時刻はオプショナル+time_sourceタグ)→ SQLiteに同一トランザクションでコミット: 現在状態(最新値)+直近履歴(時系列)+outbox(配送待ち)。電源断があっても壊れない書き方。

コミット完了後にのみack返却(ack=耐久点): accepted / duplicate / rejected / deferred。ackはエンベロープ単位のステータス配列(バッチの部分受理。未承認subject宛はdisposition: staged=承認までの有界保持、⑤参照)。送信側の保持・再送はSHOULD(fire-and-forgetの軽量プロファイルも許容。Edge側の重複排除は常に保証)。deferredは一時的過負荷専用。持続的逼迫はEdge側retention(R17劣化契約: 保持期間とディスク水位を管理し、古いものから間引き→パージ)で吸収

↓ ここから下はack後の非同期後段処理(ackはこれらを待たない)

⑨ IoTKit Site

raw canonical recordとEdge Nodeごとのcursorを同一transactionで耐久保存し、その後にaccepted-throughを返す。現在はraw queryを提供し、将来のsite-local registry・production等への意味付け・application exportのIoTKit側境界になる

⑩ YokaKit(特権なしのapplication)

Siteのapplication接続点からデータを受け取り、生産管理・帳票・ダッシュボード等の業務ロジックを所有する

AIオペレーター(データ経路には関与しない)

読み方のポイント: ①〜③が「論点1」で確定した部分です。左右どちらの経路でも、③の時点で同じエンベロープになっており(=論理契約は一つ)、運び方だけが違います(=バインディングは複数: プロセス内チャネル/UDS/HTTP/MQTT)。正規化は左では公式アダプタの中(②)、右ではデバイス作者の手元(Ⓑ)で行われ、コア(④以降)は生バイト列を一切受け取りません。契約の心臓部は④: 台帳解決(series解決)と契約検証をコミット前に実行し(D5)、ack=耐久点(SQLiteコミット完了後にのみaccepted)。⑤以降はackを遅らせない非同期の後段処理です。

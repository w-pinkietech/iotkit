>
> 本文書は、Codexメイン駆動へ移行した開発フローについて、人間の介入頻度を下げながら

## 1. 背景と目的

現在のワークフローは、設計・spec・plan・実装の各段階で独立レビューを行い、品質を守っている。
一方、次の律速が見えている。

- メインエージェントが安全側に倒れるたび、細かな設計判断まで人間へ逐次確認する。
- 複数ベンダーが同じ広い観点で全体を再走査し、壁時計時間と重複指摘が増える。
- 正常系中心の設計案をユーザーへ提示した後で、状態遷移・信頼の循環・復旧不能がレビューで見つかる。
- レビューや人間裁定の待ち時間に、依存しない作業まで停止することがある。
- セッション固有の記憶や `/tmp` 状態に依存すると、長時間の自走と再開が難しい。

目的はレビューを減らすことではない。次を同時に満たす運用を作ることである。

1. 設計ミスをレビュー前に減らす。
2. 同じ品質ゲートをより短い壁時計時間で通過させる。
3. 人間の裁定を製品上の重要判断へ集中させる。
4. 承認済みの裁量枠内では、設計からコミットまで自律的に継続できるようにする。

## 2. メインエージェントへ追加を検討する3役割

### 2.1 Flow Steward（フロー責任者）

品質ゲートを維持したまま、クリティカルパスと壁時計時間を最適化する。

- レビューを可能な限り並走dispatchする。
- レビュー対象を小さくし、変更差分・対象ハッシュ・根拠ファイル・確認事項を証拠パックにする。
- レビューベンダーごとに担当観点を分け、同じ全体調査の重複を減らす。
- 飛行中の成果物は凍結するが、依存しない成果物・調査・テスト基盤は進める。
- 同一ハッシュで既に決着した不在主張や事実を記録し、不要な再レビューを避ける。
- 修正後の確認は、指摘オーナーと意味的影響を受けるレビュアーへ限定する。
- 待ち時間、再レビュー回数、重複指摘数を計測し、速度改善が品質低下と交換になっていないか追う。

### 2.2 Design Integrity Lead（設計健全性責任者）

重要な選択肢をユーザーへ提示する前に、設計案を機械的な事前検査へ通す。

- 設計正本との整合・変更対象を明示する。
- 正常系だけでなく、失敗・競合・復旧を含む状態機械を書く。
- identity・秘密・信頼根の生成元と受け渡し経路を追跡する。
- 対象利用者の実操作を数え、技術的成立と利用可能性を分離する。
- 未確認のプラットフォーム能力を推測せず、必要なら先にread-only調査や小さなspikeを行う。
- 信頼が循環する案、不可逆操作に復旧がない案、存在しないUI・機能を前提にする案を
  「推奨案」として提示しない。

### 2.3 Autonomous Delivery Lead（自律遂行責任者）

人間が承認した目的・不変条件・非目標の範囲内では、逐次承認を待たずに進める。

- 判断を影響範囲と可逆性で Green / Yellow / Red に分類する。
- Greenは自律実行、Yellowは理由と戻し方を記録して自律実行、Redだけ人間へ上げる。
- レビュー指摘の修正・再確認・調停を、既決方針内なら自律完結する。
- 一度承認された原則の直接的帰結を、別々の人間ゲートにしない。
- Red裁定待ちでも、結果に依存しない作業を継続する。
- 停止条件に該当しない「好み」「複数の実装候補」「軽い不確実性」では停止しない。

## 3. Design Ready事前ゲート

重要なspec/design案は、外部レビューやユーザー選択の前に以下を揃える。

### 3.1 制約台帳

- 関係する設計正本と責務台帳
- 既決事項
- 今回変更する既決事項
- 非目標
- 仮定と未確認事実
- 事実・ユーザー価値判断・実装上の選択の区別

「既決設計の実装」なのか「正典を変更する新裁定」なのかを先に確定する。

### 3.2 状態機械

最低限、次の遷移を検討する。

- 初期状態と成功状態
- 同時要求
- 応答消失
- commit直前・直後の電源断
- 通常再起動
- 時計未設定・時刻ジャンプ・巻き戻り
- 期限切れ・ロック
- local recovery
- snapshot restore
- factory reset・DB欠損

### 3.3 信頼・秘密の由来

各credential・identity・鍵について次を明示する。

- 誰が、いつ、どこで生成するか
- 誰が最初に知るか
- どの経路で渡すか
- 何を信頼根として真正性を確認するか
- DB・ファイル・ログ・監査に何を保存するか
- 失効、再発行、rotation、restoreでどうなるか

### 3.4 利用者導線

各ペルソナについて実操作を列挙する。

- 入力する秘密の数
- 手入力する長い文字列
- 証明書警告・フィンガープリント照合
- SSH、SD再マウント、再起動の有無
- 失敗時に戻れる場所と次の行動
- 1台と20〜100台での繰り返しコスト
- 対象となる古いAndroid・低性能端末で成立するか

### 3.5 悪魔の6テスト

1. 同じ要求が2件同時に来たらどうなるか。
2. DB commit直前・直後に電源断したらどうなるか。
3. 成功応答だけが利用者へ届かなかったらどうなるか。
4. 時計が1970年相当から現在へ飛んだらどうなるか。
5. 古いバックアップを別の箱へ復元したらどうなるか。
6. 正当な利用者ではなく、LAN上の第三者が最初に操作したらどうなるか。

対象に応じて、ENOSPC、ネットワーク分断、秘密漏洩、送信元ローテーションも追加する。

### 3.6 Design Ready判定

以下に空白があれば、推奨案ではなく「仮説・要調査」とする。

- 全手順が実在または同一計画で実装されるコンポーネントに接続されている。
- 信頼の循環がない。
- 不可逆遷移に再試行または復旧がある。
- 同時要求の勝者と原子性境界が明確である。
- restart / restore / resetを混同していない。
- 秘密がログ、URL、argv、env、監査へ漏れない。
- 正本への追補範囲が列挙されている。
- 最も弱い対象利用者・端末でも完了可能である。

## 4. 要件から検証までの追跡

重要な不変条件は、設計機構・失敗時挙動・検証方法へ接続する。

| 不変条件 | 設計機構 | 失敗時の挙動 | 検証方法 |
|---|---|---|---|
| LAN到達だけで所有権を取得できない | ネットワークclaimを持たない | `local_setup_required` | setup mutation拒否テスト |
| reset後に旧資格情報が使えない | `auth_generation` | 全資格情報を拒否 | reset/login競合テスト |
| bootstrap判断前にAPIを開かない | import decision before bind | fail-closed | 起動順序統合テスト |

空欄がある設計は実装準備完了としない。

## 5. レビュー速度と独立性の両立案

### 5.1 3ベンダーの専門観点

同一成果物・同一ハッシュを渡すが、主担当を分ける。

- **Codex**: 実行確認、境界プローブ、並行性、データ損失、原子性、テスト現実照合。
- **Claude**: 設計正本、責務、仕様間の意味的整合、変更波及、欠落契約。
- **Grok**: 攻撃者視点、利用者導線、配布・運用・復旧、別業界パターンとの照合。

他観点の指摘を禁止するものではない。全員へ同じ広い調査を要求するのではなく、主担当を明示して
探索範囲と出力重複を減らす。

### 5.2 effortの暫定案

- 通常のspec/design確認: Codex `xhigh`、Claude `xhigh`、Grok `high`。
- 認証、データ損失、custody、restore、並行性、ハーネス変更: 担当ベンダーを必要に応じて `max`。
- 処方範囲内の確認ラウンド: `high` または `xhigh`。
- Minorのみ: 原則として次工程を止めず、台帳へ送る。

effortを下げる判断は、Critical/Importantの捕捉率と再レビュー回数を計測して再評価する。

### 5.3 結果の自律処理

- 3者が同一ハッシュでCritical/Importantなし → 自動SETTLED。
- Critical/Importantが既決方針内で修正可能 → 自律修正し、指摘オーナーへ確認。
- 処方が異なるが正本で決着可能 → メインが根拠を記録して裁定。
- 製品契約やRed判断を変更する必要がある → 人間へ上げる。
- Minorのみ → 採用または台帳送り。人間・次工程を待たせない。

## 6. 自律判断のGreen / Yellow / Red

分類はモデルの自信ではなく、影響範囲・可逆性・外部影響で行う。

### 6.1 Green — 完全自律

- 既決spec内の実装方法、内部API、モジュール分割
- テスト、エラー文言、lint、型安全性
- 既決方針を変えないレビュー修正
- 文書と実装の整合修正
- 設定化された暫定パラメータの実装

設計、実装、レビュー、コミットまで進め、マイルストーン報告に含める。

### 6.2 Yellow — 記録して自律

- 可逆な依存追加
- 非破壊migration
- 設定項目追加
- 内部性能と複雑性のトレードオフ
- 軽微なUX導線
- plan間の小規模な作業移動
- Minor指摘の採否

決定理由、戻し方、再検討トリガー、影響範囲を台帳へ残す。

### 6.3 Red — 人間裁定

- 脅威モデル・信頼境界・認証強度の変更
- データ損失、ack、custody契約の変更
- 公開wire/APIの破壊変更
- 不可逆migration
- restore / factory resetの意味論
- 対象ユーザー・製品スコープ・重要UXと安全性の交換
- 設計正本同士が矛盾し、権威順で決着できない場合
- 外部公開、push、PR、release、外部送信、費用発生等の社会的影響

## 7. 人間ゲートを減らす運用

### 7.1 裁量枠の一括承認

計画開始時に人間が次を承認する。

- 目的
- 絶対に破らない不変条件
- 非目標
- Red判断の範囲
- メインエージェントが自律処理してよい直接的帰結

承認済み原則の実装上の帰結を、別々の質問にしない。

### 7.2 判断パケット

Red判断は逐次一問ずつでなく、最大3件程度へまとめる。

- 決める事項
- Redになった理由
- 推奨案
- 代替案
- 推奨案の帰結
- 回答待ちでも進める作業

### 7.3 回答待ちでも止めない

成果物を次に分ける。

- 判断結果に依存する部分: 凍結
- どの選択肢でも必要な部分: 継続
- 現実照合・spike: 継続
- テスト基盤・契約適合試験: 継続
- 後続タスクの証拠収集: 継続

### 7.4 仮決定

可逆なYellow判断は仮決定として進める。

- 採った値・方式
- 可逆である根拠
- 変更可能な期限
- 影響範囲
- 再検討トリガー

## 8. 永続的な自走台帳

長時間の自律運転と再開のため、会話記憶やセッション固有tmpfsだけに依存しない。
採用時には保存場所と正本性を別途裁定し、最低限次を記録する。

- 現在のHEAD・工程・クリティカルパス
- SETTLED成果物と内容ハッシュ
- 飛行中レビューと待ちベンダー
- 未解決のRed判断
- Yellow仮決定と再検討トリガー
- 次の実行タスク
- 実行済みテストと結果
- ユーザー裁定と、その裁定が自律化した直接的帰結

## 9. 自律実行の停止条件

次の場合だけ人間を待つ。

- Red判断がクリティカルパスを完全に塞いだ。
- 設計正本の矛盾を権威順で解消できない。
- データ損失・秘密漏洩・認証迂回の可能性を否定できない。
- 外部公開、送信、破壊的操作、費用発生に新しい権限が必要。
- 必須レビューが全て失敗し、独立性を確保できない。
- ユーザー目的の解釈により、成果物が大きく変わる。

「好みが分かれる」「実装方法が複数ある」「可逆な軽い不確実性」だけでは停止しない。

## 10. 段階的な導入案

1. **Shadow autonomy**: メインが自律判断案を作るが、コミット前に一覧を人間が監査する。
2. **Yellowまで自律**: Green/Yellowは自動実行・コミットし、Redのみ人間裁定。
3. **Milestone autonomy**: 人間は計画開始時と最終成果確認を基本とし、途中の設計・レビュー・実装・
   確認ラウンドをメインが完結する。

候補: 計画6で段階2を試行し、重大な逆戻りがないか評価する。

## 11. 評価指標

- 1計画あたりの必須人間ゲート数
- Red / Yellow / Greenの件数と、後から分類を覆した件数
- 人間回答待ち時間と、その間に進められた独立作業量
- 実装時間、レビュー実処理時間、純待ち時間
- 同一ハッシュの重複レビュー回数
- ベンダー間の重複指摘率
- 確認ラウンド回数
- Critical/Importantの発見数と、レビュー前のDesign Readyゲートで捕捉できた数
- 自律決定のrevert率・ユーザーによる差し戻し率
- SETTLEDまでの総壁時計時間

暫定目標は「通常の1計画における必須人間ゲートを、裁量枠承認と最終成果確認の2回へ近づける」。
Red判断が生じた場合は追加ゲートを許容する。

## 12. evalで検討すべき論点

1. メインエージェント自身がYellowを過大に解釈し、実質的なRed判断を自律化しないか。
2. 3ベンダーの専門分担が、全員が同じ重大欠陥を横断的に見る独立性を弱めないか。
3. 既決事項キャッシュが、変更波及を見落として古いゼロ判定を再利用しないか。
4. Yellow判断が個別には可逆でも、累積して大きな製品変更にならないか。
5. 永続台帳が新しい正典となり、設計正本やgit実状態と競合しないか。
6. 「回答待ちでも進める」が、後で大量に捨てる投機作業を増やさないか。
7. effort引き下げが、レビュー時間ではなく再レビュー回数を増やさないか。
8. 自律コミットと、push/PR/release等の外部作用を明確に分離できているか。
9. 計画6での試行範囲、ロールバック条件、終了後の評価者をどう定義するか。

## 13. 役割規約の候補文

### Flow Steward

> Main agentは品質ゲートの管理者であると同時に、壁時計時間の最適化を担うFlow Stewardである。
> レビュー数を減らして速度を得てはならない。一方で、レビューの並走、専門観点の分担、対象差分の
> 最小化、ハッシュ単位の既決事項再利用、確認先の限定、待ち時間中の独立作業によって、品質を維持した
> ままクリティカルパスを短縮する責任を持つ。

### Design Integrity Lead

> Main agentはDesign Integrity Leadとして、重要な案をユーザーへ提示する前に、設計正本との整合、
> 状態機械、信頼・秘密の由来、失敗と復旧、対象利用者の実操作を明示する。未確認のプラットフォーム
> 能力を前提にせず、必要なら先に現実照合を行う。正常系だけで成立する案、信頼が循環する案、不可逆
> 操作に復旧経路がない案は推奨案として提示しない。

### Autonomous Delivery Lead

> Main agentはAutonomous Delivery Leadとして、承認済みの目的・不変条件・非目標の範囲内では、
> 人間の逐次承認を待たずに設計、レビュー調停、実装、検証、コミットを継続する。判断は影響範囲と
> 可逆性によりGreen・Yellow・Redへ分類し、Greenは自律実行、Yellowは理由を記録して自律実行、Redのみ
> 人間裁定とする。人間の回答待ちが発生しても、依存しない作業を進め、プロジェクト全体を停止しない。

## 14. Superpowers運用の評価とリスク適応案

### 14.1 現状評価

Superpowersの基本思想はiotkit-nextと相性がよい。

- brainstorming / spec / plan / implementation / reviewを分離する。
- 実装前に設計と受け入れ条件を外部化する。
- TDDとverificationを工程へ組み込む。
- タスク単位の変更・レビュー・コミット境界を作る。
- 会話記憶だけでなく、specとplanを再開可能な成果物として残す。

認証、restore、custody、並行性、データ損失を扱う本プロジェクトでは、これらを捨てるべきではない。
一方、現在の運用には次の重さがある。

- 変更リスクにかかわらず、同じ長さのパイプラインへ入りやすい。
- brainstormingのセクション別承認が人間をクリティカルパスに置く。
- specとplanが同じ設計説明を繰り返し、文書量とdriftが増える。
- planが関数名・コード断片まで固定し、実装中の安全な裁量を狭めることがある。
- 複数ベンダーが同じ全体調査を繰り返す。
- プラットフォーム能力の現実照合が、外部レビューまで遅れることがある。

評価上の中心命題は、Superpowersを廃止することではなく、**固定された儀式からリスク適応型の
開発コンパイラへ変えられるか**である。

### 14.2 変更リスク別のパイプライン

#### Small — 低リスク

対象例:

- 原因と期待動作が明確なバグ修正
- 文言・ドキュメント整合
- 既決設計内の内部リファクタ
- 既決テストの追加

候補フロー:

```text
現実確認 → failing test → 修正 → verify → targeted review → commit
```

独立した長文spec・詳細planは原則不要。ただし公開契約や不変条件へ波及した時点で上位へ再分類する。

#### Medium — 中リスク

対象例:

- 設定項目の追加
- 非破壊migration
- 内部API変更
- 局所的な新機能
- 可逆な依存追加

候補フロー:

```text
短いdesign note → Design Ready → targeted cross-vendor review
→ 簡潔な実装計画 → 自律実装 → integration review
```

#### Large / Red — 高リスク

対象例:

- 認証・認可・秘密管理
- 公開wire/API契約
- データ保持・ack・custody
- restore / factory reset
- 脅威モデル
- crate境界や責務の大幅変更

候補フロー:

```text
Mission Brief → Design Ready → brainstorming → spec → 3ベンダーレビュー
→ plan → planレビュー → task実装・レビュー → final integration review → PR
```

計画6はこの区分に属する。

### 14.3 brainstormingの変更候補

現行のセクション別逐次承認を、次へ置き換える案を評価する。

1. 人間が最初に目的・不変条件・非目標・Red判断範囲を承認する。
2. メインエージェントが設計全体を作る。
3. Design Ready事前ゲートへ通す。
4. Green/Yellowは自律確定する。
5. Red判断だけを最大3件程度の判断パケットにまとめる。
6. 裁定後はspec完成まで自走する。

「ユーザーの価値判断が必要な設計」を省略するのではなく、同じ原則の帰結を何度も承認させない。

### 14.4 writing-plansの変更候補

planは実装コードの代筆ではなく、実装者の裁量を安全に制約する成果物へ寄せる。
各タスクの必須内容候補:

- 達成する契約・不変条件
- 変更可能範囲と禁止範囲
- 依存する前タスク
- 最初に書く失敗テスト
- 完了条件と検証コマンド
- 独立レビューの重点
- コミット境界
- 失敗・中断時の戻り方

関数内部、逐語的コード、正確な補助関数名まで固定するのは、契約上必要な箇所に限定する。
実装中により単純で安全な形が見つかった場合、specの意味を変えない範囲でGreen判断として採用できる
余地を残す。

### 14.5 維持すべき要素

次は速度のために弱めない。

- 設計と実装の分離
- TDD
- verification before completion
- 設計正本との照合
- 独立したクロスベンダーレビュー
- タスク単位の意図的なコミット
- Critical/Important修正後の確認規律
- 同一内容ハッシュに結びつく消費ゲート
- データ損失・認証・並行性の明示確認
- git / disk / testによる現実照合

### 14.6 軽量化候補

- 全変更に長大なspecを要求すること
- 全変更に詳細planを要求すること
- 設計セクションごとの人間承認
- Minorのみの再レビュー待ち
- 全ベンダーが同一観点で行うフル走査
- 内部実装を過剰に固定するコードスニペット
- 可逆なGreen/Yellow判断での全体停止

軽量化は「ゲートを削除する」ではなく、リスクに応じて不要な成果物と重複作業を省くものとする。

### 14.7 推奨パイプライン候補

```text
Mission Brief
  ↓
Risk classification
  ↓
Design Ready preflight
  ↓
リスクに応じたspec/design
  ↓
専門分担した並列レビュー
  ↓
Redのみ人間裁定
  ↓
契約中心のplan
  ↓
自律的な実装・テスト・コミット
  ↓
タスク単位targeted review
  ↓
最終統合レビュー
  ↓
人間へのマイルストーン報告
```

### 14.8 evalで追加確認する事項

1. Small / Medium / Largeの分類者と、上位再分類の機械的トリガーを定義できるか。
2. 軽量フローでも設計正本・公開契約への波及を検出できるか。
3. 短いdesign noteとspecの境界が曖昧にならないか。
4. 契約中心planが、実装ワーカーへ必要な現実情報を不足なく渡せるか。
5. コードスニペット削減が型名・API名のdriftを増やさないか。
6. targeted reviewが、変更差分外の波及を見落とさないための昇格条件を持てるか。
7. リスク適応による短縮時間と、後戻り・再レビュー増加を同時に測定できるか。
8. 計画6ではLargeフローを維持したまま、どの承認・重複調査だけを安全に減らせるか。

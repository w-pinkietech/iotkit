# D11: 入口認証と流入制御 (R2/R19入口側)

Status: 決定 (2026-07-08)
用語は [../terminology.md](../terminology.md)、責務は [../responsibility-ledger.md](../responsibility-ledger.md) に従う。
査読: クロスベンダー2社(codex gpt-5.5 / Claude Fable)に同一プロンプトで査読させ、両者一致のCritical
(絞りをD1の終端 `rejected` に写像しない——ワイヤ表現の明示、入口リスナー有効化を工事層の独立操作に
分離——device addの暗黙副作用禁止)と、片側の重要指摘(検算のdevice addごと実行+capacity_debt、
失効時の活きたMQTTセッション切断、流量クラスの帰属単位=認証送信者、ペアリング窓経路の強度条件、
絞り振動のヒステリシス、fire-and-forget送信者への正直さ、staged sightingの承認待ちピン留め、
site_local_cidr、staleトークン報告、契約プロファイル名の固定)をすべて本文へ反映した(2026-07-08)。

## 背景

R19の三方向(入口R2 / 出口R10 / 制御面R12-15)のうち、出口はD10で確定した。本決定は入口側を埋める。

入口の骨子はD1/D5が既に多くを保持している——per-deviceトークン(共有禁止・ハッシュ保存・
ワンタップ失効+再発行・漏れる前提)、subjectスコープ認可、送信者ID=認証主体から導出、
解決チェーンと侵害シグナル、curl 3行クイックスタート、予約済み契約(key_id rotation・HMAC署名・
per-deviceクォータ・単調seq・失効理由コード)。本決定はそれらを統合確認し、残る空白
(脅威モデル・流入制御・トークンの一生・登録の儀式・目撃ステージング有界化・露出制御)を確定する。

ユーザー裁定による前提(変更する場合は本決定の改訂を要する):

1. **脅威モデル**: サイト内LANは「社内の廊下」(D10と同一)。入口特有の主役は**悪意ではなく事故**——
   出来の悪い自作デバイスの流量暴走、壊れたセンサーのゴミ値、設定コピーによる身元混同。
2. **対応の階段**: 絞る=自動可、検疫=自動可(既決の枠)、トークン失効=人間のみ。
   自動対応は必ず騒がしく行う(アラーム+R23現場表示+監査)。
3. **責任の境界**: 容量設計(ハード選定・通信経路・台数)は現場エンジニアの責任。ソフトは
   (1)宣言の保存と検算 (2)公平な執行 (3)正直な報告、の番人に徹する。学習型の自動判定は不採用。
4. **現場に負担をかけない**: 既定クラスで登録時に何も考えなくてよい。厳密な事前テストは不要。
   curl 3行の体験は不変。

## 決定1: 入口の脅威モデル——守るのは共有物

入口はOSS公約(柱2)により第三者の自作デバイス(ESP32等)を受け入れる面である。事故で壊れるのは
データベースではなく**共有物**——ディスク、書き込み体力(保存してからackを返すコスト)、電波、
他デバイスの取り分、R17劣化契約までの余裕。1台の暴走が現場全体のデータ保全を巻き添えにする構造を、
流入制御(決定4)で仕切る。

ソフトウェアは自分で問題を「解決」しようと賢く振る舞わない。**宣言された契約を執行し、破れたら
報告する**——申告制(決定4)はこの原則の実装である。挙動を学習して逸脱を自動判定する方式は、
絞られた理由を現場に説明できず、誤検知で正常なデバイスを止める危険があるため不採用。

## 決定2: 送信者identityと認証(D1/D5既決の統合確認)

- 送信者IDは常に**認証主体**から導出する(D1)。HTTP/MQTT=トークンが指すdevice_id、
  プロセス内=source申告が主体。
- per-deviceトークン(共有キー禁止)、ゲートウェイ側はハッシュ保存、subjectスコープ認可
  (トークンに書き込み可能なsubject集合を束縛)、解決チェーンはコレクタが実行(D5)。
- 他送信者の既知subjectへの解決=rejected+侵害シグナル監査、経路Cトークンの未知subject_hint=
  rejected(D5)。
- **無認証の受信面は存在しない**。唯一の例外はペアリング窓の登録コード(決定6)で、それも
  単回使用・短TTL。
- MQTT ingestバインディング: username=device_id / password=トークン(D1既決)。
- 経路はTLS+フィンガープリントピン(D3)。平文は明示opt-in+警告ログ(D1既決)に加え、
  **プライベートアドレス限定**をMUSTとする(D10決定8と同型。WAN越えの平文入口は構成として拒否)。

## 決定3: デバイストークンの一生——長命を既定とする(出口と逆)

出口の束縛credential(D10決定3)は短命+2スロット+無人再発行だが、**入口のデバイストークンは
長命を既定**とする。非対称の理由:

- 出口の相手は自分たちのソフトウェア(ゲートウェイ/[3])であり、前倒し更新と無人再発行の機械を
  実装できる。入口の相手は**第三者のファームウェア**であり、rotation儀式を強制すると柱2の低摩擦
  (curl 3行、ESP32趣味工作の受け入れ)が壊れる。
- 漏洩対策は寿命ではなく4枚の壁で受ける: (1)subjectスコープ(漏れたトークンで書ける範囲が狭い)
  (2)ワンタップ失効+再発行(D1) (3)流量クラス(漏れたトークンでも申告枠内しか流せない=決定4)
  (4)LAN限定露出(決定7)。
- rotation(key_id)・HMAC署名・単調seq厳格検証はD1の契約予約のまま維持し、高脅威現場向けの
  opt-inとして残す(発動条件の設計は保留)。ただし**契約プロファイル名は今固定する**:
  `simple_bearer`(既定・第一波実装) / `signed_seq`(HMAC署名+単調seq) / `provisioned_key`(将来)。
  名前だけ先に決めて契約の穴を塞ぎ、実装は必要になった現場から(業界照合: Home Assistantの
  長命トークン=低摩擦の先例、AWS IoTの短命claim→恒久credential交換=provisioned_keyの先例)。

**失効は人間のみ**(AIハーネスは提案+根拠提示まで)。D10の中間層(出口credential失効=AI可)と
逆に見えるが、整合している——出口の失効はmake-before-break+無人再発行があり何も沈黙しないのに対し、
入口の第三者デバイスには無人再発行経路がなく、**失効=そのセンサーの沈黙**という不可逆な運用判断に
なるため。失効には理由コードを付す(D1予約の具体化)。

- **失効は活きたセッションも切る**: デバイストークン失効は、当該device_idの活きたMQTT ingest
  セッションの強制切断と連動する(D10決定3と同じ理由——MQTTは接続中credentialの失効を自然には
  伝えない。接続時認証のままでは失効済みデバイスが再接続まで送信し続ける)。
- **「忘れられた失効」の手当て**: R12にトークンの最終使用時刻と長期未使用(stale)トークンの報告を
  持つ。長命既定の下で「失効=人間のみ」を成立させるための判断材料(業界照合: AWS IoTの
  last-used報告と同型)。

replace-hardware(D5)・デバイス廃棄時は旧トークンの失効を必須項目とする。

## 決定4: 流入制御は申告制(流量クラス)

各デバイスは登録時に**流量クラス**(粗い段階制の想定流量)を持つ。

- **既定クラスあり**——`device add` はクラスを指定しなければ既定値になり、登録体験は変わらない
  (現場負担ゼロ)。真面目な現場は導入前に見積もってクラスを選ぶ——その見積もりの質が
  現場エンジニアの責任、執行がソフトの責任(ブレーカー盤の分担: アンペア選定=工事士、
  遮断=ブレーカー)。
- クラスの段階・具体値・絞りのアルゴリズム(トークンバケット等)はWave 1で実測して確定する。
- **検算は一度きりにしない**: 申告合計 vs 実測体力の検算は、導入検査(Phase 6)に加えて、
  **`device add`・クラス変更のたびに事前条件検査(R14)として実行**する——全デバイスが既定クラスの
  まま台数だけ増える現場で、超過が誰にも警告されずに進行し最後の砦R17で初めて露見する経路を塞ぐ。
  超過時は追加を黙って拒否せず、**人間の明示承認付きで通して超過分を `capacity_debt` として記録**する。
  申告合計/実測体力の水位はR12に常時公開する。

運転中の執行の階段:

| 段 | 発動 | 動作 | 主体 |
|---|---|---|---|
| 通常受理 | クラス内 | 保存してack | — |
| **絞る** | クラス超過 | 超過分を**非終端**の応答で退ける(ワイヤ表現は下記)。可逆・枠内復帰で自動解除(ヒステリシス付き) | システム自動+騒がしく(アラーム+R23+監査) |
| **検疫** | ゴミ値・範囲外・登録直後 | 保存と可視化は継続、下流配送とアクション駆動から外す(既決の枠。時限自動失効) | システム自動(既決)+騒がしく |
| **失効** | 運用判断 | 締め出し。復帰には再発行 | **人間のみ**(AIは提案まで) |

- **執行機構はD1既決**(per-deviceレート制限+グローバル上限、429+Retry-After)。本決定が確定するのは
  (1)枠の**出所**=申告された流量クラス(D1予約「per-deviceクォータ」の具体化)、
  (2)自動化の範囲=上記の階段、(3)自動対応は必ず騒がしく行うこと、の3点である。
- **絞りのワイヤ表現(D1のack語彙と衝突させない)**: 絞りは**非終端**であり、D1の終端 `rejected`
  (決定的契約違反専用・送信側spool除去対象)には**決して写像しない**——rejectedに乗せると、spoolを
  持つ善良な送信者が超過分を恒久削除してしまう(絞り=可逆のはずが送信側でデータ破壊)。
  HTTPは429+Retry-After(リクエスト処理前の遮断、耐久ackなし)。ack語彙に乗せる場合は `deferred`
  (一時的過負荷専用=D1と整合)。バッチの部分超過はエンベロープ単位のdeferredで表現する。
- **クラスの帰属単位は認証送信者**(トークンまたはプロセス内source)。衛星アダプタ等の多subject送信者
  (1トークン=多デバイス)は配下デバイスの合算を申告する——執行単位(per-deviceレート制限=認証送信者
  単位、D1)と申告単位を一致させる。
- **振動対策**: 絞りの解除はヒステリシス/クールダウンを持ち(2閾値の先例=D1の水位)、絞りアラームは
  継続状態として集約する(発報はエピソード単位)。境界上でバーストするデバイスがアラームを乱打し、
  「騒がしさの原則」がアラーム無視の訓練に転化するのを防ぐ。具体値はWave 1。
- **spoolなし送信者への正直さ**: fire-and-forget送信者(ackを読まないESP32等)にとって、絞りは逆圧では
  なく**データ破棄**である。契約文書に「spoolなしプロファイルではクラス超過分は失われる」と明記し、
  破棄件数・対象期間(`throttled_drop_count`)をR12/R23/監査に出す。
- **R17との関係**: 流量クラスは公平の仕切り、R17劣化契約は最後の砦。クォータが全て正常でも
  R17は発動しうる(申告合計が実容量を超える構成ミス等)。仕切りは砦を置き換えない。

## 決定5: 事故・悪意入力への耐性(受理面の細目)

D1のDoSハードニングが既に基礎を決めている——認証検証をボディ読み込み前に(未認証は確保ゼロで即401)、
ボディ上限、タイムアウト、同時接続上限、ingress→コアの有界キュー(満杯503シェッド)、
dedup台帳のTTL+サイズ上限。本決定はそれを確認した上で、次を追加確定する。

- **認証失敗の監査+失敗レートのスロットリング**(同一送信元の連続失敗を減速——本決定の新規確定)。
- **目撃ステージングの有界化**(D5「有界・パージ可能」の実体の確定): staged sightings(未知hardware_idの
  観測保持)は**送信者ごと**と**全体**の2段の上限(件数・保持期間)を持ち、超過は最古から破棄する。
  破棄は監査に残し、ステージング上限到達はアラームを上げる(BLEスキャナが隣の工場のビーコンを
  拾い続ける・バグでランダムIDを量産する、への防壁)。上限値はWave 1で確定。
  ただし**承認待ち・replace-hardware候補・人間が確認画面で開いている候補**としてマーク済みの
  hardware_idの目撃は破棄対象から保護(ピン留め)する——最古破棄が交換復旧の材料(D5の観測プロファイル)
  を消さないため。同一送信者経由の洪水(正当な新デバイスと隣工場のビーコンが同じBLEアダプタから
  届くケース)でも、承認待ち分が守られる。
- dedup台帳が洪水時に縮退した(良性送信者の重複保護が薄まった)ことを監査に残す。

## 決定6: 登録の儀式(D1/D2既決の確認+精密化)

D1が既に骨格を決めている——時間制限付きペアリングウィンドウ+デバイス上のワンタイム登録コード+
**人間のタップ承認(AIは提案まで)**+登録直後は検疫ステート。`device add` で台帳エントリ+
system_id採番+トークン発行が一体(D2/D5)。本決定の追加確定:

- **登録の2経路とコードの束縛**を明確化する:
  - **帯外経路(既定・curl 3行)**: `device add` → トークンを画面表示 → 人間がデバイス設定へ貼り付け。
    **ネットワーク上に無認証の交換は存在しない**。
  - **ペアリング窓経路(デバイス発)**: 窓の開放中のみ、未登録デバイスがネットワーク越しに登録要求を
    出せる。登録コードは {ペアリング窓ID, ゲートウェイTLSフィンガープリント(配布用), 単回使用秘密,
    短TTL} の束(D10登録券と同型の構造)であり、これが**唯一の無認証面**。強度条件を必須とする:
    コードの最低エントロピー、送信元ごとの試行減速+試行回数上限、窓ごとの失敗アラーム、
    人間承認画面でのdevice fingerprint/短縮ID突合(取り違え防止)。具体値はWave 1。
- ペアリング窓は明示的に開閉し、**開けっ放しを禁止**する(自動クローズ)。
- **トークン衛生**を契約ガイドの必須項目にする: 一回表示(再表示はせず再発行)、ログ・スクリーン
  ショット・平文設定ファイルへの書き出し禁止(credential_tokenをDebug/ログに出さない既決と同族)、
  デバイスのfactory resetで消去、廃棄・譲渡時は失効。
- **共有ファームウェアイメージへのトークン焼き込み禁止**(D8決定5の原則を自作デバイスにも適用)。
  ESP32を量産する場合、ファームは共通・トークンは個体ごとに投入する。焼き込むと同一identityの
  デバイスが量産され、入口でも身元衝突事故が起きる——契約ドキュメントで明示警告する。

## 決定7: 入口リスナーの露出制御

- ネットワーク入口(HTTP/MQTT ingestリスナー)は**既定でオフ**。**有効化は独立した工事層操作**
  (型付き・監査付き)であり、`device add` の暗黙の副作用にしない——日常操作が攻撃面のスイッチを
  暗黙に倒す抜け道(工事層の迂回)を作らないため。bind先の変更・プロトコル(HTTP/MQTT)の追加も
  同じく工事層。**有効化済みリスナーへの**ネットワークデバイス登録は日常操作のまま。
  公式アダプタのみの現場(第一号現場を含む)は入口の攻撃面ゼロのまま——D1の「Wave 1で
  トークン/TLS/DoS実装」の判断と整合。
- bind先は明示設定の **`site_local_cidr` +許可インターフェース**で定義する(「LAN限定」の検証可能な
  実体。決定2の平文規則=プライベートアドレス限定と同じ基準)。別拠点・第三者WiFi・VPN越しの
  プライベートアドレスは「サイト内LAN」として扱わない——D10の経路クラス規則に従い、トンネルまたは
  別ゲートウェイ+出口契約へ回す。**入口リスナーをインターネットへ公開しない(MUST)**。
  遠隔地からデータを入れたい構成は、入口の公開ではなく「遠隔地に別のIoTゲートウェイ[2]を置き、
  出口契約([3]/[4]向け)で運ぶ」で受ける——入口は常にサイトの中の門である。
  ホスト型サイトサーバー(D10)でもこの規則は変わらない(トンネルは[2]↔[3]の出口側経路であり、
  入口リスナーはLAN側のまま)。衛星アダプタ(D2 §4)もこの帰結として**サイトLAN内経路のみ**
  (インターネット越えの衛星アダプタは構成として認めない。D2 §4へ注記)。

## 決定8: 入口操作の権限写像(D10の2層との整合)

※本表の「人間のタップ承認」はD12決定3(2026-07-08)で**日常層**として正式化された。南向き動詞の写像はD12決定3。

| 操作 | 権限 |
|---|---|
| device add(登録承認)・ペアリング窓の開閉 | **人間のタップ承認**(D1既決。AIは提案まで)。現場の日常作業であり、D10の工事層ではない——ただし**入口リスナーが有効化済みであることが前提**(初回有効化は工事層=決定7) |
| **流量クラスの変更** | **人間のみ**(AIは提案まで)。申告=エンジニアの宣言であり、絞りアラームを受けてAIが自分でクラスを引き上げられると申告制の仕切りが無効化するため |
| 検疫の解除 | 時限自動失効またはAI/人間による解決(D1既決の枠) |
| デバイストークン失効 | **人間のみ**(理由: 決定3の非対称——失効=センサーの沈黙)。スマホからワンタップ(D1既決) |
| トークン再発行(失効済みデバイスの復帰) | 人間のワンタップ(D1既決) |
| 入口リスナーの有効化・bind変更・プロトコル追加・平文opt-in | 工事層(人間のみ。攻撃面と経路の変更のため。日常操作の暗黙副作用として発動させない=決定7) |
| 絞り | 操作ではなくシステムの自動執行(決定4) |
